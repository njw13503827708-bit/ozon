# Ozon 整批上传确认闸门设计

## 背景

当前项目已经具备 1688 商品采集、本地工作台、商品资料生成、图片生成与质检、Ozon 多店提交和失败恢复能力。现有主流程将新批次默认设置为自动上传，商品通过图片质检后可以直接进入 `ozon_upload`。项目也保留了一套运行前人工确认以及单商品等待上传的旧逻辑，但它们都不满足“整批全部生成完毕后，只读审阅一次，再统一授权上传”的要求。

本次改造在生成阶段和 Ozon 写入阶段之间增加整批上传确认闸门。它不增加逐商品确认，不允许在最终确认页直接编辑，也不改变库存边界。

## 目标

- 用户选择一批商品、SKU、最终 Ozon 类目和目标店铺后，可以运行完整的离线生成与质检流程。
- 所有商品生成成功并通过硬性质量检查后，批次进入一次性的整批上传确认页。
- 确认页只读展示结果摘要和风险；需要修改时返回现有工作台。
- 任一商品失败、未完成或未通过硬性质量检查时，整批禁止确认，Ozon 写调用保持为零。
- 用户一次确认后，系统才允许批次中的商品进入现有多店 Ozon 提交流程。
- 重复点击、服务重启和失败重试不得导致成功商品或已取得 `task_id` 的店铺重复提交。

## 非目标

- 不在最终确认页编辑标题、价格、属性、SKU、图片或店铺。
- 不新增库存、仓库、激活、订单、广告或 ERP 功能。
- 不改变商品资料生成、图片生成或 Ozon payload 的业务算法。
- 不引入新的外部 AI API。
- 不将历史商品、测试素材或其他商品目录作为当前批次输入。

## 推荐方案

在现有 15 步流水线中保留 `ozon_upload` 步骤，但为工作台生产批次增加批次级授权条件。商品完成 `image_qc` 后进入 `READY_FOR_BATCH_REVIEW`，而不是直接执行上传。批次协调器只有在全部商品都满足上传前条件时，才把批次标记为 `AWAITING_BATCH_UPLOAD_CONFIRMATION`。

确认动作生成持久化的批次授权记录。流水线只有在授权记录与当前批次内容哈希一致时，才能调度 `ozon_upload`。这样不需要复制生成批次为另一个上传批次，也不会把批次一致性建立在浏览器内存或单商品状态上。

未采用的方案：

- 复用单商品 `WAITING_MANUAL_REVIEW`：改动较小，但无法可靠表达整批原子阻断，容易出现部分商品提前上传。
- 新建独立上传子批次：隔离清晰，但需要复制商品、店铺、失败恢复和审计状态，复杂度超过当前需求。

## 状态模型

### 商品状态

- `READY_FOR_BATCH_REVIEW`：商品具备上传资格，当前批次可以将其纳入确认摘要。
- 现有失败与关注状态继续表示生成、字段、图片或输入问题，不改写为“可确认”。
- 确认通过后，商品恢复为可调度状态，`current_step` 和 `next_action` 指向 `ozon_upload`。

实现可以只持久化 `READY_FOR_BATCH_REVIEW`，并将“仍在等待同批商品”作为批次派生展示状态；不应为相同事实维护两个互相竞争的权威字段。

### 批次状态

- `RUNNING`：至少一件商品仍在执行上传前步骤。
- `BLOCKED_BEFORE_UPLOAD`：至少一件商品失败、未通过质检或存在硬阻断，整批不可授权。
- `AWAITING_BATCH_UPLOAD_CONFIRMATION`：全部商品均已准备好，等待一次整批授权。
- `UPLOAD_AUTHORIZED`：授权已持久化且哈希有效，可以调度上传。
- 后续继续使用现有上传中、部分失败、等待 Ozon 结果和完成状态。

批次状态由商品状态、上传前检查和授权记录派生并持久化，不能仅凭前端页面状态决定。

## 上传前资格条件

批次进入可确认状态前，每件商品都必须满足：

- 正式输入仍属于当前 `product_id + collection_id`。
- SKU 快照存在且数量不超过 10。
- 最终类目、目标店铺和每个 SKU 的 offer 标识齐全。
- `ozon-attributes-final.json`、`ozon-upload-config.json` 和 `ozon-draft.json` 已生成并通过现有安全校验。
- 所需图片存在，图位绑定完整，图片硬性质量检查通过。
- 商品没有活动失败、待人工问题或未完成步骤。
- 每个目标店铺都处于允许创建、更新或安全重试的状态。
- 请求体不包含库存字段，也不需要调用库存、仓库或激活接口。

任何一项不满足，都在确认摘要中形成硬阻断，并将批次置为 `BLOCKED_BEFORE_UPLOAD`。

## 批次确认摘要

新增只读接口：

`GET /api/workbench/batches/{batch_id}/upload-review`

返回：

- 批次 ID、商品数、SKU 数、目标店铺和预计提交条数。
- 每件商品的中文来源标题、俄文最终标题、最终类目、SKU、价格、主图和目标店铺。
- 属性覆盖率、未知字段数、估算字段数、图片检查结果。
- 按 `blocker`、`warning`、`info` 分类的风险项。
- `can_confirm`、阻断计数和警告计数。
- 基于当前待提交内容生成的 `review_hash`。

摘要必须来自最终上传产物和权威状态，不得从仅供展示的商品级汇总反推 payload。

## 内容哈希与授权记录

`review_hash` 至少覆盖以下稳定序列化内容：

- 批次 ID 和商品 ID 列表。
- 每件商品的 collection ID 与 SKU 运行快照。
- 最终类目、目标店铺、最终价格和 offer 标识。
- 最终属性、最终俄文文案、图片清单及图片文件 SHA-256。
- Ozon 草稿或最终请求体的规范化哈希。

确认接口：

`POST /api/workbench/batches/{batch_id}/confirm-upload`

请求只包含用户看到的 `review_hash`。服务端重新执行全部资格检查并重新计算哈希。只有批次仍可确认且哈希完全一致时，才原子写入授权记录。授权记录包含批次 ID、哈希、操作者、确认时间、商品列表、目标店铺和审计版本。

商品资料、SKU、类目、价格、图片、店铺或最终请求体发生变化时，重新计算的哈希不同，旧授权自动失效。授权不得只保存在浏览器状态中。

## 确认页交互

最终确认页为只读页面，包含：

- 顶部批次摘要：商品数、SKU 数、店铺数、预计提交数和当前状态。
- 商品列表：缩略图、标题、SKU 数、价格范围、属性覆盖和图片检查状态。
- 商品详情摘要：俄文标题、最终类目、SKU 与图片、关键属性和风险来源。
- 风险区：硬阻断、警告和提示分组展示。
- 底部操作：`返回工作台修改` 和 `确认整批上传`。

存在任何硬阻断时，确认按钮禁用。警告不阻止确认，但按钮附近明确显示警告数量。返回工作台只导航到现有编辑入口，不在确认页创建第二套编辑状态。

## 流水线行为

1. 用户在工作台创建批次并启动任务。
2. 商品执行现有上传前步骤，直到 `image_qc` 和最终字段收口完成。
3. 每件成功商品进入批次审阅就绪状态，不调用 Ozon 写接口。
4. 批次协调器汇总所有商品：
   - 全部通过：进入 `AWAITING_BATCH_UPLOAD_CONFIRMATION`。
   - 任一失败或未通过：进入 `BLOCKED_BEFORE_UPLOAD`。
5. 用户查看整批只读摘要。
6. 如需修改，返回工作台；修改后仅重新执行受影响步骤，旧授权失效。
7. 用户点击整批确认；服务端复检并持久化授权。
8. 批次进入 `UPLOAD_AUTHORIZED`，现有调度器按照 `ozon_write_concurrency` 的并发限制执行多店提交。
9. 单店失败沿用现有隔离与重试；成功、处理中或已取得 `task_id` 的店铺不得重传。

## 失败与恢复

- 上传前失败不会写授权记录，也不会调用 Ozon 创建、更新、只读回查或库存接口。
- 服务重启后从批次文件、商品状态、授权记录和 SQLite 店铺发布记录恢复。
- 确认请求重复发送且哈希相同，应返回同一授权结果，不重复排队。
- 确认请求的哈希过期，返回 HTTP 409，并要求刷新确认摘要。
- 确认时出现新的硬阻断，返回 HTTP 409；批次回到 `BLOCKED_BEFORE_UPLOAD`。
- 确认后单店提交失败不撤销其他店铺的成功结果；重试只针对明确失败且尚未取得 `task_id` 的店铺。
- 日志记录状态变化、阻断原因、摘要哈希、授权操作者、时间和上传调度结果，但不记录店铺密钥。

## 安全边界

- 开发、测试和离线验收必须使用替身客户端或严格网络拦截，Ozon 写调用为零。
- 真实 Ozon 提交只能发生在配置有效店铺凭证、批次授权有效且用户点击整批确认之后。
- 不提交库存字段，不调用库存、仓库或激活接口。
- 不覆盖 `input/source.json` 或原始图片。
- 不复用其他商品、历史批次或测试目录的素材。
- 已提交商品、历史 payload、任务号和 SQLite 发布记录不可删除或重写。

## 测试策略

采用测试优先开发：

- 状态机测试：商品完成上传前步骤时必须停在批次闸门。
- 整批阻断测试：任一失败、未完成或质检不通过时 `can_confirm=false`，Ozon 写调用为零。
- 摘要合同测试：只读摘要正确聚合商品、SKU、店铺、风险和最终产物。
- 哈希测试：稳定输入生成稳定哈希；任一受保护内容变化都会使旧哈希失效。
- 确认接口测试：只允许一次整批确认，拒绝缺少商品、过期哈希、重复排队和越权批次。
- 恢复测试：服务重启后仍能识别待确认、已授权和已提交状态。
- 多店测试：单店失败不重传成功店铺，已取得 `task_id` 的店铺保持幂等。
- UI 测试：确认页无编辑控件，阻断时按钮禁用，返回工作台和确认动作正确。
- 安全回归：所有离线测试断言 Ozon 写调用和库存调用均为零。

验证顺序：定向单元测试、全量 Python 测试、React 工作台构建、Edge 插件构建、项目离线自检、浏览器界面验证和离线端到端批次演练。

## 运行与交付

实现完成后使用 Windows 本地工作台运行。首次运行需要安装 Python 依赖并构建 React 工作台和 Edge 插件。没有真实商品输入或有效店铺凭证时，只执行离线演练，不伪造正式商品或尝试真实提交。

当前 ZIP 未包含 Git 元数据，因此设计与实现可以在解压工作副本中完成和验证，但无法保留原始提交历史或创建正常 Git commit。最终交付包含修改后的项目目录、启动说明、测试结果和可重新打包的 ZIP。
