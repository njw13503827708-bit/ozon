## Identity and safety decisions

- `organization_id` is required for every organization-owned record; `store_id` and `platform` are required where an entity belongs to a marketplace store. Canonical Product/SKU are not falsely tied to a single marketplace. Their external identities live on Listing/Review bindings. `external_id` may be null when the platform has not supplied a verified ID; never substitute Ozon `Client-Id` or a category ID for Seller ID.
- Internal IDs are stable JLC IDs. Unique remote identities are scoped by `(platform, store_id, external_id)` when `external_id` is known. Product, SKU, Listing, Review, and Draft remain distinct entities.
- Every entity must retain an unambiguous path to `organization_id`; marketplace-owned entities also retain `platform` and `store_id` directly or through a required parent. Remote `external_id` is recorded where supplied, never invented. Canonical Product/SKU may map to several stores/platforms through Listings; local-only Draft/Analysis records inherit the Review's marketplace identity and have no fabricated remote ID.
- All external marketplace writes, including review replies, remain disabled. No inventory/warehouse/activation operation is added. No production mock/fallback data in Store, Product, or Review Center.
- One Default Organization is used now. This is schema groundwork, not users, JWT, RBAC, or a multi-tenant security claim. APIs must not expose arbitrary organization switching before authorization exists.
- SQLite remains the local runtime database; migrations and repository boundaries should avoid assumptions that block a later PostgreSQL transition. PostgreSQL deployment is not part of V1.1B.
- The existing `PREVIEW -> CONFIRM -> EXECUTE` Ozon product-write gate and Task 7–11 behavior are unchanged. Tests use mocks and temporary databases; live Ozon read sync requires separate user approval.
