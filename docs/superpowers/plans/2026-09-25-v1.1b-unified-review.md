# V1.1B Unified Marketplace Foundation + Review Center Implementation Plan

> **For Codex:** Approved for implementation on 2026-09-25. Keep `demo-v1.1a` frozen and work only in `v1.1b-development`.

**Goal:** Deliver a cross-platform ERP data foundation and a basic, read-only Review Center while preserving the verified V1.1A Ozon workflow and keeping every marketplace write disabled.

**Architecture:** Extend the existing FastAPI + React + SQLite ERP Repository/Service/Adapter boundaries. Internal Product and SKU are canonical; Store, Channel, Listing, and Review carry platform-scoped remote identity. Add local-only Reply Draft and an AI analysis result contract, not an AI pipeline. PostgreSQL remains a future storage option, not a migration in this release.

**Tech Stack:** Python/FastAPI/sqlite3/unittest; React/TypeScript/Vite; existing build and self-check commands. No new framework or runtime dependency is planned.

**Spec:** `docs/superpowers/specs/2026-09-25-v1.1b-unified-review-scope.md`

**Status:** Implementation approved by the user on 2026-09-25.

## Execution boundaries and acceptance criteria

- Execute only in the `v1.1b-development` worktree. Do not edit `demo-v1.1a`, its runtime, real `products/` or `batches/`, credentials, or a real Ozon store.
- Preserve old Task 12 Organizations, Task 13 Store Center, Task 14 Product Center, Task 15 Legacy Index, and Task 16 Final Verification. Their substance is mapped below; the added work does not silently remove them.
- Existing V1.1A Tasks 1–11, Seller Identity semantics, listing reconciliation, attribute persistence, cooperative cancellation, CredentialStore/Windows ACL, and `PREVIEW -> CONFIRM -> EXECUTE` remain unchanged except for directly caused regressions.
- External marketplace write routes, review send routes, inventory operations, and production mock/fallback data are out of scope. Ozon writes = 0; Inventory writes = 0.
- Each implementation task starts with a failing contract test, then the minimum change, then focused tests. After each task, run affected V1.1A regression tests. Do not delete/skip a failing test to manufacture a green result.
- Final gate: complete Python suite `failures=0, errors=0`; document baseline/final skip diff; Command Center typecheck/build, Edge extension build, `project_self_check` all PASS. Real Ozon read verification requires separate approval; no approval means it stays pending, not fabricated.

### Task 2 (B2) — Unified Marketplace Data Foundation

**Files:** `backend/db/erp.py`, `backend/repositories/erp.py`, `migrations/009_unified_marketplace_foundation.sql`, `tests/test_unified_marketplace_schema.py`, `tests/test_unified_marketplace_repository.py`.

1. RED: assert existing Product/SKU/Listing rows survive migration; all organization-owned rows receive a non-null `organization_id`; a marketplace external identity cannot collide within `(platform, store_id)`; canonical Product/SKU IDs stay distinct from Listing IDs.
2. Add `marketplace_accounts` and `marketplace_channels`. Link Store to an account where known, without moving or duplicating plaintext secrets. Add organization and generic remote-identity columns to existing Product/SKU/Listing only where the entity owns such an identity; keep the existing Ozon-specific columns for compatibility.
3. Define internal IDs independently from remote IDs. Product/SKU receive organization scope; Listing receives platform, store, optional channel, and verified `external_id`. Account/Store/Channel retain platform and verified external IDs when available. Unknown external IDs remain null; never infer Seller ID from `Client-Id` or category tree.
   Every new table has an auditable path to organization scope; marketplace-owned rows also have a path to platform and Store. Local-only Draft/Analysis rows inherit that mapping from Review. Canonical Product/SKU map to multiple marketplaces via Listings rather than a forced single Store.
4. Extend existing `sync_jobs` and `audit_logs` with organization/platform/store context. Add `sync_cursors` keyed to organization + platform + store + entity type, with an opaque cursor and last-success timestamp. Reuse current cancellation/retry/status behavior; no new queue runner.
5. Add repository reads/writes and DB constraints for the new fields. Do not build a generic identity framework or migrate to PostgreSQL.
6. Run schema/repository tests and current Ozon product-sync/reconciliation tests; require PASS and unchanged Ozon semantics.
